# PR Writing

让没有参与开发的人读完说明后，知道这次变更解决什么问题、如何影响使用者，以及哪些地方需要重点审阅。

## 先确定说明对象

- 读取适用的 `AGENTS.md`、`CONTRIBUTING.md` 和 PR 模板。遵守仓库的格式、语言与交付规则；未指定语言时，标题用英文，正文用中文。
- 确认 PR 的目标分支与当前 head，读取整个分支相对目标分支的差异。现有 PR 文案、提交消息和关联 issue 是辅助背景，不能代替实际改动。
- 对堆叠 PR，区分本次新增变化与父分支已有变化。尚未提交的改动不能写成远端 PR 已包含的内容。
- 如果只能看到部分差异或缺少背景，明确评价范围；不要补造动机、验证结果或兼容性承诺。

## 写清变化与理由

开头交代原来的行为或缺口，再说明这次产生的具体结果。涉及多处实现时，按能力、行为或责任划分组织内容，避免逐文件复述 diff。

有重要设计选择时，说明选择了什么、为何适合当前约束，以及相关代价或保留风险。只有实际考虑过且与评审有关的替代方案才值得写；不要为了显得完整而编造方案比较。

术语应帮助评审者定位问题。例如描述并发控制时，说明它保护的行为或约束，再补充实现术语。把失败、取消、重试和恢复行为放在相关设计说明中，不混入“未验证”事项。

标题遵守仓库已有约定；没有约定时使用 `type(scope): concrete change`，scope 可省略。表达当前整份变更的主要结果，避免 `update`、`cleanup`、`address feedback` 这类缺少对象和结果的标题。

## 按变更规模组织

- 小改动可以只写一小段，不为填满模板之外的栏目扩写内容。
- 功能或缺陷修复，可采用“背景／主要改动／验证”等自然分节，按实际内容取舍。
- 涉及 API、数据格式、权限或存储契约变化时，说明受影响的使用方、兼容性与必要迁移。
- 跨模块变更可提供简短的评审顺序。图示、前后对比和示例只在能降低理解成本时加入。
- 有可见 UI 变化时，优先提供可打开且与当前代码一致的前后对比。标注关键状态和比较基线；缺少真实基线或截图时，直接说明限制。

## 让验证结论可判断

保留影响评审判断的证据：覆盖了什么行为、使用什么测试环境、结果如何，以及哪些范围仍未验证。例如，应区分模拟服务测试与真实服务互通。

检查结果只能来自实际执行记录或当前 CI 状态。分别表述已通过、失败、进行中和未运行；不能把计划、源码快照一致或某个检查通过推断为完整验证。

正文概括关键结论，必要时链接可访问的记录。完整日志、反复尝试过程、个人交接过程和常规检查流水放到 issue 或任务记录中。仅在精确命令有助于复现问题或验证特殊行为时保留命令。

## 更新与交付

- 实现范围或设计发生实质变化后，重新检查整份标题和正文，使其描述最终结果；不要追加“第几轮又改了什么”的开发日记。
- issue 引用必须有可核对的来源。确实解决并应关闭的问题使用 `Closes`，仅关联背景使用 `Refs`。
- 仅评估说明时，给出总体判断和重要的可执行建议，不把写作评价冒充代码正确性审查。
- 写文案或评估 PR 不自动授权提交代码、推送、发布、修改远端 PR 或合并。若当前任务已经明确授权其中某项操作，按已有授权执行，不重复索取确认。
- 获准发布或更新后，回读远端标题、正文、base/head 和附件，确认渲染正确且内容对应当前变更。
